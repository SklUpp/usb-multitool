# Кандидаты в диагностику и Ventoy: критическая оценка

Дата: 2026-11-22. Статус: **аналитика, код кандидатов не реализован**.
Требования к будущей работе зафиксированы в
[requirements/2026-11-22-docs-review-candidates.md](requirements/2026-11-22-docs-review-candidates.md).

Оценка проверяет не только идею, но и её посадку в текущий код. «Принято» ниже
означает «имеет смысл проектировать», а не «можно включать в релиз сейчас».

## Сводка

| № | Кандидат | Вердикт | Главное ограничение |
|---|---|---|---|
| 1 | SMART через ATA PASS-THROUGH (16), `0x85` | Условно принято, первый приоритет | SAT не гарантирован; нужен probe и whitelist read-only ATA-команд, парсер вендорских атрибутов |
| 2 | Быстрый детектор поддельной ёмкости по идее f3probe | Условно принято только как destructive-диагностика | Тест пишет на диск и может уничтожить разметку/данные; автоматический запуск запрещён |
| 3 | `persistence.dat` для Ventoy через `f_expand` | Условно принято, средний объём | `FF_USE_EXPAND` выключен, готового API нет; непрерывность и file-backed block device нужно доказывать |
| 4 | Восстановление таблицы по VBR | Не готово, требуется переработка | 1 MiB — не универсальный шаг; `TableInitializer.gptPlan` создаёт пустую таблицу и не принимает найденные разделы |
| 5 | SCSI UNMAP/TRIM, `0x42` | Отложено | LBPME недостаточно; нужны VPD Block Limits, free-space semantics и отдельный стенд |

## 1. SMART через ATA PASS-THROUGH (16)

### Что верно

- `0x85` — действительно CDB ATA PASS-THROUGH (16) из семейства SAT. Он
  позволяет передать ATA-команду через SCSI-транспорт; SMART READ DATA и
  IDENTIFY DEVICE возвращают 512-байтные блоки.
- Команду можно сделать read-only: фиксированный CDB, `ScsiDirection.IN`,
  `transferLength = 512`, без произвольного ATA-командного поля от UI.
- Текущий слой уже подходит как основа: `ScsiCdb` хранит 16 байт, направление и
  длину (`ScsiCommand.kt:14-33`), `READ CAPACITY(16)` уже реализован
  (`ScsiCommand.kt:84-93`), а `UsbDisk.transfer` умеет BOT/CSW/sense-retry
  (`UsbDisk.kt:127`).
- Для типового USB-SATA/NVMe-моста это дешёвая и полезная функция: модель,
  температура, reallocated sectors, износ — без записи на носитель.

### Что неверно или преувеличено

- **«Поддерживается всеми внешними SSD и переходниками» — неверно.** SAT —
  опциональная функция моста/прошивки. smartmontools содержит отдельные
  USB-адаптеры и обходы для Cypress, JMicron, Prolific, Sunplus и др.; часть
  мостов понимает только 12-байтный вариант или требует vendor-specific
  обход. Ответ `ILLEGAL REQUEST` — нормальный сценарий, а не исключение.
- **«0 рисков» — неверно.** Неправильный `PROTOCOL`, длина или ATA-команда
  могут привести к зависанию моста. Безопасность даёт не «read-only CDB», а
  жёсткий whitelist: IDENTIFY DEVICE и SMART READ DATA, проверка ATA status в
  sense, таймауты и запрет произвольных команд.
- **«+15 строк в ScsiCommand.kt» — недооценка.** Нужны:
  - capability probe (IDENTIFY DEVICE) и различение «мост не умеет»/«диск не
    ответил»;
  - разбор Descriptor Format Sense Data и ATA Status Return descriptor;
  - парсер 512-байтного SMART-блока: 30 атрибутов по 12 байт, начиная со
    смещения 2; ID `0x05` — reallocated sectors, но temperature и wear —
    вендорские (часто `0xC2/0xBE`, `0xE7/0xE9/0xB1`), а не универсальные;
  - обработка «атрибут отсутствует», «raw value vendor-specific», температурный
    raw может быть в разных байтах;
  - тесты на фикстурах разных вендоров и на мосте без SAT.
- **«smartmontools — готовый парсер» — только частично.** У smartmontools есть
  таблицы атрибутов и drive database, но они не являются публичным API и
  покрывают не все вендоры. Переносить нужно идею, а не тащить весь проект.
- IDENTIFY и SMART READ DATA — две разные ATA-команды. Если нужна модель/серийник,
  это отдельный проход; серийник также доступен через SCSI INQUIRY VPD `0x80`.

### Безопасный дизайн

1. Открыть диск эксклюзивно, не монтировать ФС.
2. Отправить ATA PASS-THROUGH (16), protocol 4 (PIO Data-In), ATA IDENTIFY
   DEVICE (`0xEC`), `CK_COND=1`, таймаут.
3. Если sense = `ILLEGAL REQUEST`/`INVALID COMMAND` — показать «SMART не
   поддерживается», не повторять бесконечно.
4. Только после успешного IDENTIFY отправить SMART READ DATA (`0xB0`, feature
   `0xD0`) и разобрать атрибуты.
5. Не давать UI передавать ATA opcode/feature; всё — константы native/Kotlin
   слоя.
6. Показывать «нет данных», если атрибут отсутствует; не подставлять 0.

**Оценка объёма:** примерно 250–400 строк с тестами и мостом, не 15.

**Критерии приёмки:** на SAT-мосте получены модель/температура/атрибуты; на
мосте без SAT — аккуратный отказ без потери сессии; ни один write-CDB не
отправлен; парсер проверен на фикстурах минимум двух вендоров.

## 2. Быстрый детектор поддельной ёмкости (f3probe)

### Что верно

- Идея f3probe жизнеспособна: запись/чтение в адресах за пределами реальной
  ёмкости выявляет контроллер, который зацикливает адреса или подменяет
  ответы.
- Это **не** read-only тест. Даже «безопасный» маркер пишется в секторы,
  которые пользователь считает данными; при аппаратном зацикливании возможна
  перезапись начала диска.
- Полное тестирование H2testw действительно не нужно для грубого детектора;
  логарифмическая выборка резко сокращает число операций.

### Что нельзя обещать

- **«1 секунда / <64 I/O»** — не контракт. Время зависит от USB-моста,
  таймаутов, размера логического блока, скорости записи и поведения
  зацикленного контроллера. На плохом мосте один запрос может висеть секунды.
- **«Подделка гарантированно перетирает только sector 0»** — модель, а не
  гарантия. Разные контроллеры зацикливают по-разному; тест может испортить
  MBR/GPT, VBR, beginning of first partition или вернуть ложный результат.
- Обычный `DestructiveConfirmation.request` показывает предупреждение, но не
  делает операцию безопасной. Для такого теста нужен отдельный режим с
  точной идентификацией диска, объявленной ёмкостью и явным вводом
  подтверждения, а не только кнопка «Продолжить».
- Нельзя запускать тест на диске, где есть смонтированные тома или
  незавершённые операции; нужен эксклюзивный claim и запрет фонового запуска.

### Безопасный дизайн

- Только раздел **Диагностика**, только вручную, только после отдельного
  предупреждения: «Будет записан тестовый маркер. При подделке возможна потеря
  разметки и данных».
- Показывать точную модель, серийник, заявленную ёмкость и LBA теста.
- Сначала read-only проверки; запись — только после подтверждения.
- После теста сообщать «признаки подделки»/«не удалось проверить», а не
  ставить диагноз «подделка» без повторяемого evidence.
- В тестах использовать выделенный фейковый образ/устройство, не рабочий USB.

**Вердикт:** функция уникальна для мобильного приложения, но это
destructive-инструмент, а не «принято с 0 рисков». Реализовывать после SMART и
только с отдельным UX/стендом.

## 3. `persistence.dat` / VHD для Ventoy

### Что верно

- Ventoy поддерживает persistence-файл на первом разделе. Официальный
  `CreatePersistentImg.sh` создаёт `persistence.dat`, делает ext2/3/4 или XFS и
  метку (`casper-rw` и т.п.), затем файл подключается через Ventoy persistence
  plugin.
- FatFs R0.16 действительно содержит `f_expand` (около `ff.c:5757`), и при
  `opt=1` он пытается выделить непрерывный файл без записи нулей. Это хороший
  примитив для создания образа без многоминутного `dd`.
- Ext4 в проекте уже есть: `ExtFs.mkfs(device: BlockDevice, label)` принимает
  `BlockDevice` (`ExtFs.kt:88`), а `VirtualPartition` даёт range-checked view
  (`VirtualPartition.kt:10`).

### Что неверно или не готово

- **«Уже скомпилировано» — нет.** В `third_party/fatfs/source/ffconf.h`
  `FF_USE_EXPAND` равен `0`; `f_expand` вырезан препроцессором. Нужно включить
  опцию, пересобрать native, добавить JNI-обёртку и проверить ABI/размер типов.
- **«Файл 4 ГБ гарантированно единый extent» — нет.** `f_expand` вернёт
  `FR_DENIED`, если нет непрерывного участка. Это нужно показывать как
  штатную ошибку с предложением очистить/дефрагментировать носитель.
- **«0.3 секунды» — не измерено.** Время зависит от FAT/bitmap, USB и
  фрагментации; на телефоне это может быть заметно дольше.
- **`VirtualPartition` не является file-backed устройством.** Он принимает
  `startLba` и `disk`. Чтобы форматировать ext4 **внутри FAT-файла**, нужен один
  из двух путей:
  1. отдельный `BlockDevice`, который читает/пишет кластеры файла через FatFs
     (медленно, зато без обхода FAT и без требования непрерывности);
  2. contiguous-extent adapter: `f_expand` резервирует цепочку, приложение
     получает физические LBA и работает с ними напрямую, но обязано закрыть
     `FIL`, не писать через FatFs и сохранить валидную цепочку/размер файла.
     Второй путь быстрее, но требует тщательной проверки crash-safety.
- **Нет поддержки persistence plugin в `ventoy.json`.** Текущий код умеет
  `control`/`auto_install`, но не создаёт запись вида `persistence` с привязкой
  файла к ISO. Без этого созданный `persistence.dat` не будет выбран при
  загрузке. Нужен явный редактор/валидатор plugin-секции, а не только файл.
- **VHD — другой сценарий.** Ventoy умеет загружать VHD(x), но это не то же
  самое, что persistence ext4. Нельзя смешивать «persistence.dat» и «VHD» в
  одном обещании.

### Безопасный дизайн

- Размер и ФС выбираются явно; для >4 ГиБ — только exFAT (FAT32 лимит),
  ext4 создаётся через file-backed adapter.
- До записи: проверить свободное место, `f_expand` результат, фактическую
  непрерывность и свободный диапазон.
- Если `FR_DENIED` — ничего не создавать, показать «нужен непрерывный блок
  N ГиБ; очистите/дефрагментируйте».
- После создания: `sync`, проверить размер/метку/ФС, добавить запись в
  `ventoy.json` только после валидации JSON и точной привязки к ISO.
- При crash: файл может остаться пустым/частичным; нужен cleanup только
  созданного файла и повторная проверка перед записью.

**Оценка:** это не «мгновенная функция на 0.3 секунды», а средний
native+storage+JSON проект. Начинать с `FF_USE_EXPAND=1` только после
прототипа contiguous extent и теста на фрагментированном exFAT-образе.

## 4. Восстановление разметки по VBR (модель TestDisk)

### Что верно

- VBR содержит полезные поля: exFAT `PartitionOffset` на 64 и `VolumeLength`
  на 72 (Microsoft exFAT spec), NTFS total sectors на 40, FAT32 total sectors
  на 32, hidden sectors на 28.
- Сканирование VBR — read-only и может помочь, когда MBR/GPT потеряны, а
  начало раздела известно или восстановимо.
- TestDisk действительно умеет искать потерянные разделы по сигнатурам и
  предлагать восстановление; это правильная модель, а не «магия».

### Что неверно или опасно

- **«VBR на каждом 1 MiB» — только распространённое выравнивание.** MBR может
  начинаться с LBA 63, 2048, произвольного значения; GPT — с произвольного
  выровненного/невыровненного LBA. Скан только по 1 MiB пропустит старые и
  нестандартные разметки и даст ложное «ничего не найдено».
- **«64 точки за <100 мс»** не гарантируется: каждый VBR — отдельный SCSI
  read через USB BOT; 64 команды могут занять заметно больше.
- **`TableInitializer.gptPlan` не принимает найденные разделы.** `plan()` и
  `gptPlan()` создают **пустую** таблицу; `Plan` не содержит списка записей
  (`TableInitializer.kt:46-71`, `149`). Передать туда VBR-параметры нельзя —
  нужен новый recovery planner и запись GPT entry array с GUID/типами/именами.
- Из VBR нельзя восстановить GPT GUID раздела, имя, атрибуты и точный тип.
  Можно восстановить геометрию и эвристически тип ФС; этого достаточно для
  MBR-подобного восстановления, но не для «точного GPT за 1 клик».
- Нужна проверка пересечений, candidate scoring, подтверждение каждого
  раздела и явный выбор: primary GPT / backup GPT / VBR candidates. Запись
  «найденной таблицы» — destructive и должна идти через существующие
  confirmation/fencing-механизмы.

### Безопасный дизайн

- Сначала прочитать и проверить существующие primary и backup GPT; VBR-скан —
  только fallback.
- Сканировать не только 1 MiB, а набор стратегий: MBR-цепочка, известные
  выравнивания, VBR-сигнатуры; bounded по времени/числу операций.
- Строить кандидатов с offset/size/type/confidence; не писать автоматически.
- Показывать карту «найдено/пересекается/неоднозначно»; запись — отдельной
  кнопкой после подтверждения точной геометрии и capacity hash.
- Тесты: MBR 63, 2048, GPT, unaligned, exFAT/NTFS/FAT32 fixtures, overlap и
  отсутствие backup.

**Вердикт:** идея ценная, но текущая оценка «готово к 1 клику» неверна. Это
самый большой проект из пяти после TRIM.

## 5. SCSI UNMAP / TRIM (opcode `0x42`)

### Что верно

- `0x42` — SCSI UNMAP; логические блоки освобождаются, это «trim» для
  thin-provisioned/SSD-устройств. Команда может ускорить носитель и продлить
  ресурс, если применена к свободным блокам.
- `LBPME` в READ CAPACITY(16) — один из признаков logical block provisioning.
  `sg_unmap` также указывает на LBPU/ANC_SUP в VPD-странице и лимиты
  `MAXIMUM UNMAP LBA COUNT` / `MAXIMUM UNMAP BLOCK DESCRIPTOR COUNT` в Block
  Limits VPD page `0xB0`.
- Ограничение одним дескриптором — разумная консервативная мера против
  кривых мостов, но это не доказанная универсальная защита.

### Что неверно или опасно

- **Проверять только LBPME недостаточно.** Нужно проверить VPD Block Limits,
  Logical Block Provisioning VPD, logical block size и optimal unmap
  granularity; иначе можно отправить неверный диапазон/размер и получить
  `ILLEGAL REQUEST` или зависание.
- **«4 КиБ выравнивание» — не универсально.** LBA и granularity задаёт
  устройство; 4 КиБ — частый, но не единственный размер. Нельзя хардкодить
  без проверки.
- **UNMAP разрушает данные в диапазоне.** Это не безобидный «flush». Для
  файловой системы нужно знать свободные кластеры и не задевать метаданные;
  для раздела — не задевать таблицу и чужие ФС. Без layer-а free-space
  semantics это опасный инструмент.
- **«>1 descriptor вешает JMS567/JMS578»** — правдоподобный vendor bug, но
  неподтверждённое обобщение. Даже один дескриптор не гарантирует отсутствие
  зависания на плохой прошивке; нужен стенд и таймаут/аборт.
- TRIM на USB-мосте может быть эмулирован, проигнорирован или возвращать
  success без фактического освобождения. Это нужно явно писать в UI.

### Безопасный дизайн (если когда-либо)

- Сначала read-only probe: RC16 LBPME, VPD `0xB0`, LBP VPD, логический размер.
- Отдельный destructive-сценарий только для **свободного диапазона**,
  вычисленного ФС; никогда не «trim весь диск» по кнопке.
- Один дескриптор, granularity из VPD, таймаут и обязательный `SYNCHRONIZE
  CACHE`; после — readback/статус, но не обещание ускорения.
- Тест только на выделенном стенде; не на пользовательском носителе.

**Вердикт:** не «второй приоритет после базовой диагностики», а отдельный
рискованный проект. Сначала SMART и восстановление, затем измеримый TRIM на
стенде.

## Что это значит для очереди

1. SMART — делать первым, как read-only диагностику с честным «не
   поддерживается».
2. Восстановление по VBR — вторым, но после переработки API и стратегии
   сканирования; это не «1 клик из текущего `gptPlan`».
3. Persistence — третьим, после прототипа `f_expand` + file-backed ext4 и
   plugin-записи в `ventoy.json`.
4. f3probe — только как явно destructive-инструмент, после отдельного UX и
   стенда.
5. TRIM — не включать в ближайшую волну.
