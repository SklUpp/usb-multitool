# Требования: документация, ревью и оценка кандидатов

Дата: 2026-11-22. Статус: зафиксировано до информационного анализа и
реализации. Документ задаёт границы задачи; найденные факты и выводы — в
[feature-candidates.md](../feature-candidates.md).

## Цель

1. Обновить документацию под фактическое состояние `c5e916b`.
2. Провести комплексное независимое ревью всех правок после `a73d18e`.
3. Дать критическую информационную оценку пяти кандидатам, не выдавая
   неподтверждённые утверждения за факты.

## Обязательные требования

- R1. Документация должна отделять проверенное поведение от предположений и
  планов; ссылки на код и стандарты обязательны.
- R2. Ревью покрывает все изменения `a73d18e..HEAD`: UI/state, FAT/JNI/ext4,
  USB/SAF/files и связанные тесты. Ревьюер не правит рабочее дерево.
- R3. Каждая находка ревью получает severity, точный якорь и проверяемый
  сценарий; родитель подтверждает её до исправления.
- R4. Для каждого кандидата фиксируются: реальная ценность, зависимости,
  деструктивность, минимальный проверяемый объём и условия отказа.
- R5. Нельзя утверждать, что функция уже готова, если код выключен флагом,
  API отсутствует или поведение зависит от прошивки/вендора.
- R6. Деструктивные кандидаты не реализуются и не запускаются в этой задаче;
  достаточно требований и безопасного дизайна.
- R7. Изменения кода допускаются только для исправления подтверждённых
  ревью-дефектов; новые фичи кандидатов — отдельная задача после согласования.
- R8. Проверки: targeted unit/host tests, компиляция, `git diff --check`;
  отсутствие device-проверки указывается явно.
- R9. Итоговые документы: `progress.md`, `ui.md`, `filesystems.md`,
  `architecture.md` (при необходимости), `docs/README.md` и отдельный
  `feature-candidates.md`.

## Кандидаты: границы оценки

| № | Кандидат | Обязательное условие перед реализацией |
|---|---|---|
| 1 | S.M.A.R.T. через ATA PASS-THROUGH (16), opcode `0x85` | Только whitelisted read-only ATA-команды; capability probe и корректный разбор sense; поддержка бриджа не предполагается. |
| 2 | Быстрый детектор поддельной ёмкости по идее f3probe | **Снят:** destructive-тест не имеет доказуемого OS-unmount на non-root Android. Read-only capacity preflight — отдельная функция, не f3. |
| 3 | `persistence.dat` для Ventoy через `f_expand` | `FF_USE_EXPAND` сейчас `0`; нужно включить, создать file-backed block device и обработать `FR_DENIED`; непрерывность — оптимизация, не требование Ventoy (persistence backend может быть фрагментирован); «гарантия 4 ГБ» запрещена. |
| 4 | Восстановление таблицы по VBR | VBR-скан только чтение; 1 MiB не считать универсальным шагом; не использовать пустой `TableInitializer.gptPlan` как готовый API; запись только после подтверждения точной геометрии. |
| 5 | SCSI UNMAP/TRIM, opcode `0x42` | Проверять VPD Block Limits/LBP, а не только LBPME; granularity брать у устройства; учитывать free-space semantics и деструктивность; отложить до отдельного стенда. |

## Вне задачи

- Реализация S.M.A.R.T., f3probe, persistence, восстановления по VBR и TRIM.
- Изменение partition/FAT write semantics ради кандидатов.
- Проверки на физическом USB, TalkBack, IME, RTL и реальном рендере.
- Push и CI-прогон не являются условием анализа; публикация — только после
  принятия результатов родителем.

## Критерии готовности

- Документы отражают `c5e916b`, включая FAT streaming, JNI-helper и UI-волну.
- Независимое ревью завершено вердиктом; подтверждённые дефекты исправлены или
  явно вынесены с причиной.
- Оценка кандидатов содержит источники и не содержит ложных «100% готово»,
  «0 рисков» и «все бриджи поддерживают».
- `feature-candidates.md` связан из индекса документации.
- Выполнены заявленные targeted-проверки; ограничения перечислены.

## Фаза «параллельный ресерч внедрения» (2026-11-22)

Цель — не код, а доказательные implementation dossiers по пяти кандидатам.
Требования действуют до изменения этого документа.

- R10. Пять независимых read-only research lanes; никаких правок рабочего
  дерева, Gradle/NDK-сборок и физических destructive-тестов.
- R11. Каждый dossier обязан содержать:
  - реальные точки интеграции с точными `file:line`;
  - новые API/структуры/состояния и их владельцев;
  - порядок выполнения и crash/abort/retry semantics;
  - UX и confirmation gates, включая disabled/read-only состояния;
  - тест-матрицу: unit/host/fixture/device-required;
  - оценку diff-объёма и зависимости между кандидатами;
  - явный verdict `go`, `conditional` или `no-go` с причиной.
- R12. Внешние факты подтверждаются первоисточниками (T10/Microsoft/Ventoy/
  smartmontools/f3/TestDisk); анекдоты о прошивках помечаются как
  неподтверждённые.
- R13. Для SMART и TRIM нельзя обещать поддержку без capability probe; для
  f3probe и TRIM destructive-путь не проектируется как автоматический.
- R14. Для persistence обязательно проверить `FF_USE_EXPAND`, file-backed
  `BlockDevice`, ext4 mkfs и `ventoy.json` plugin, а не только создание файла.
  Фрагментация persistence backend допустима; `f_expand` — опциональная
  оптимизация, а не условие корректности Ventoy.
- R15. Для recovery обязательно проверить существующие GPT backup/fencing
  APIs; `gptPlan` не считать API восстановления.
- R16. Родитель независимо проверяет ключевые anchors и внешние факты; итог
  сводится в `feature-candidates.md` без дублирования полных отчётов.
- R17. Приоритетный порядок внедрения определяется по ценности, риску,
  зависимостям и проверяемости, а не по исходной нумерации.
- R18. В этой фазе запрещены commit/push, если пользователь отдельно не
  попросил; результаты остаются в рабочем дереве/отчёте.
- R19. Разрешено переиспользовать и адаптировать готовый сетевой OSS-код
  (smartmontools, f3, TestDisk, Ventoy, SCSI helpers), если лицензия совместима
  с GPL-3.0-or-later приложения. Источник и ревизия фиксируются, уведомления и
  GPL-обязательства сохраняются.
- R20. Предпочтителен минимальный адаптер/порт алгоритма, а не импорт целого
  проекта. Никаких runtime-загрузок кода; зависимости фиксируются в
  `third_party`/`scripts/fetch-third-party.sh` с проверяемой ревизией.

## Решение пользователя (2026-11-22)

- В этой волне реализуется **только SMART**. Recovery, persistence A,
  safe-capacity preflight и NTFS/ext write session **задокументированы и
  отложены**; новые code lanes по ним не запускаются.
- Для будущего persistence выбран **file-backed FatFs adapter** (вариант A),
  поддерживающий фрагментированные файлы; реализация отложена.
- f3probe **снят с очереди**. Исследование показало: на non-root Android 28–36
  доказуемого OS-wide unmount нет, experimental-режим после system eject не
  считается безопасным. Destructive-код не включать; read-only capacity
  preflight, если понадобится, проектируется отдельно и не называется f3.
